# Okta SSO/SCIM 电子邮件不匹配

Claude 使用电子邮件作为主要标识符来匹配 SSO 登录和已配置的座位。在 Okta 中，SCIM 配置和 SSO 是分别配置的，可以从不同的用户配置文件字段中提取电子邮件。本指南说明如何识别和解决不匹配问题。

**适用于：**使用 SCIM 配置的企业计划和 Console 组织。Team 计划没有 SCIM 配置，因此不适用此不匹配场景——请参阅**[设置 JIT 或 SCIM 配置](https://support.claude.com/en/articles/13133195)**了解每个计划上的可用功能。

---

## 症状

人员在尝试通过 SSO 访问您的组织时可能会遇到以下一种或多种情况：

- **“账户创建被阻止”**——SSO 身份验证成功，但 Claude 无法找到匹配的已配置账户。如果您的组织限制了组织创建（推荐），该人员将被完全阻止。

- **登陆到免费个人账户**——如果未限制组织创建，该人员将完全绕过您的组织，创建或登陆到免费个人账户，而不是其已配置的座位。

- **“检查您登录的账户”不匹配**——SSO 回调显示的电子邮件与该人员在登录时输入的电子邮件不同。

- **Claude Code 身份验证失败**——Claude Code CLI 在身份验证流程中显示电子邮件不匹配错误。

---

## 发生原因

Okta 用户配置文件包含多个代表身份的字段。SCIM 配置（在**配置 → 到应用**下）和 SAML/OIDC SSO（在**登录**下）是独立配置的。

| **Okta 属性**     | **典型值**                               | **常用于**                        |
| --------------- | ------------------------------------- | ------------------------------ |
| `user.login`    | `testuser1` 或 <testuser1@example.com> | 默认 SCIM userName 映射；有时为 NameID |
| `user.email`    | <test.user.one@example.com>           | SAML/OIDC 电子邮件声明（推荐）           |
| `appuser.email` | 应用级用户电子邮件覆盖                           | 自定义应用级属性映射                     |

常见的不匹配：SCIM 使用 `user.login`，而 SAML 发送 `user.email`。Claude 需要完全匹配的字符串。

**常见混淆：**Okta 的 SCIM 属性映射和 SAML 属性语句位于两个不同的选项卡中——SCIM 在**配置 → 到应用**，SSO 在**登录**。

---

## 诊断步骤

### 步骤 1——确认不匹配

1. **检查 SCIM 电子邮件：**导航到**应用 → [Claude 应用] → 配置 → 到应用 → 属性映射**。找到 `email`（或 `userName`）行。**值**列显示正在发送的 Okta 表达式。

2. **检查 SSO 电子邮件 (SAML)：**转到**应用 → [Claude 应用] → 登录 → SAML 设置 → 编辑 → 属性语句**。找到 `email` 属性。**值**列指示哪个 Okta 字段被断言。

3. **检查 SSO 电子邮件 (OIDC)：**转到**应用 → [Claude 应用] → 登录 → OpenID Connect ID 令牌**并查看**声明**部分中的电子邮件。

4. 如果 SCIM 和 SSO 值引用不同的 Okta 字段，则确认不匹配。

### 步骤 2——确定问题范围

- **大多数或所有已配置人员受影响：**这是系统属性映射问题。修复在您的 IdP 的 SCIM 属性映射中。

- **一两个人员受影响：**问题特定于这些账户。直接检查其用户配置文件。

### 步骤 3——直接验证 Okta 用户配置文件

1. 转到**目录 → 人员 → [用户] → 配置文件**。

2. 比较登录和电子邮件字段值。这些字段之间的差异将产生映射不匹配。

---

## 解决方案

### 将两个映射对齐到同一 Okta 字段

最安全的修复是对 SCIM 和 SSO 都使用 `user.email`，因为此字段包含 Okta 中的规范电子邮件地址。

1. **更新 SCIM 映射：**在**配置 → 到应用 → 属性映射**中，将 `email`（或 `userName`）源更改为 `user.email`。

2. **更新 SSO 声明 (SAML)：**在**登录 → SAML 设置 → 属性语句**中，将电子邮件属性值更改为 user.email。

3. **更新 SSO 声明 (OIDC)：**在**登录 → OpenID Connect ID 令牌 → 声明**中，更新电子邮件声明以映射到 `user.email`。

4. 点击“保存。”

### 强制完全重新同步

**关键——需要完全同步：**增量同步不会在您更改属性映射后更新现有记录。

1. 在**配置 → 到应用**中，点击“强制同步”以触发对所有已分配人员的完全重新评估。

2. 或者，对于特定人员：**配置 → 推送用户 → 选择受影响的人员 → 立即推送**。

3. 检查 Okta 系统日志（**报告 → 系统日志**）中的配置错误。

4. 在人员重试登录前，验证更新的电子邮件值是否出现在配置日志中。

---

## 修复后清理

更正属性映射并完成完全同步后：

- **流氓免费账户：**如果修复前未限制组织创建，某些人员可能已创建免费个人 Claude 账户。请联系**[我们的支持团队](https://support.claude.com/en/articles/9015913)**进行删除。

- **幽灵账户（错误电子邮件座位）：**原始配置的具有不正确电子邮件的账户可能仍然存在于您的组织中，占用永远无法使用的座位。请联系我们的支持团队进行取消配置。

- **座位可用性：**如果幽灵账户占用了所有合同座位，即使映射已修复，新登录也会因座位不足错误而失败。

- **重新添加受影响的人员：**删除幽灵账户后，具有更正电子邮件的人员可能需要重新邀请或重新配置。

- **防止未来发生：**在您的组织的身份和访问设置中启用“限制组织创建”，以防止未配置的人员创建免费账户。

---

## 验证

完成修复和任何清理后：

1. 检查已配置人员的样本——确认配置日志中的其电子邮件与 SSO 发送的电子邮件格式匹配。

2. 要求受影响的人员清除 claude.ai 的浏览器 Cookie，然后通过 SSO 登录。他们应该直接登陆到您的组织工作区，不出现错误。

3. 确认人员未创建免费账户——限制组织创建后，被阻止的人员会看到清晰的错误，而不是登陆到个人账户。

4. 如果 Claude Code 受到影响，让该人员重新运行 `claude auth login --enterprise` 并确认电子邮件与其已配置的座位匹配。

## 常见问题

| **问题**                                                | **解决方案**                                                 |
| ----------------------------------------------------- | -------------------------------------------------------- |
| 管理员更新 SAML 声明但忘记 SCIM 属性映射（或反之）                       | 两者都必须更新。SCIM 映射在**配置 → 到应用**下；SAML 声明在**登录 → SAML 设置**下。 |
| `user.login` 对某些人员包含用户名（不是电子邮件）                       | 切换两者为 `user.email` 并验证所有人员的电子邮件字段已填充。                    |
| 增量同步运行但电子邮件未更新                                        | 属性映射更改后需要**强制同步**或**推送用户**。                              |
| 应用级配置文件属性 (`appuser.email`) 与用户配置文件 (`user.email`) 不同 | 检查应用级属性映射是否覆盖用户配置文件值。                                    |
| 电子邮件已更新但人员仍无法登录                                       | 查找流氓免费组织或幽灵账户。清除浏览器 Cookie 并重试。如果问题持续，请联系支持。             |
| OIDC 和 SAML 应用是 Claude 的单独 Okta 应用                    | 某些组织配置两者。确保两个应用中的属性对齐。                                   |

- SCIM 和 SSO 属性看起来相同，但人员仍无法访问其座位。
